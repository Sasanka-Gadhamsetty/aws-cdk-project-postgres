# AWS CDK Project — Event-Driven Serverless Orders Pipeline (Postgres)

This stack (`AwsCdkProjectStack`) implements an asynchronous order-processing
pipeline using Lambda, SNS, SQS, and EventBridge, fronted by an API Gateway
REST API, backed by **Aurora Serverless v2 (Postgres)** instead of DynamoDB.
A separate stack (`CdkS3Stack`) still holds the standalone S3 bucket from
before — untouched.

## Architecture

```
Client
  │
  │ POST /orders           GET /orders/{id}
  ▼                              ▲
API Gateway ──► CreateOrderFunction   GetOrderFunction ──► Aurora Postgres
                     │                                  (via RDS Data API)
                     │ writes PENDING row                    ▲
                     ▼                                        │
              Aurora Postgres (orders table)                  │
                     │                                         │
                     │ publish "OrderCreated"                  │
                     ▼                                         │
              SNS Topic (order-events-topic)                   │
                 │                    │                        │
     (fan-out)   │                    │                        │
                 ▼                    ▼                        │
   order-processing-queue   order-audit-queue                  │
                 │                    │                        │
                 ▼                    ▼                        │
     ProcessOrderFunction      AuditOrderFunction               │
        (sets PROCESSED) ──────────────────────────────────────┘
                 │
                 │ PutEvents "OrderProcessed"
                 ▼
      Custom EventBridge Bus (order-event-bus)
                 │
                 ▼
      EventBridge Rule (source: custom.orders)
                 │
                 ▼
      OrderProcessedHandlerFunction (sets audited_at) ──► Aurora Postgres
```

The SNS/SQS/EventBridge/API Gateway topology is identical to the DynamoDB
version — only the data layer changed.

### Why Aurora Serverless v2 + RDS Data API (not a "normal" RDS instance)

- **Serverless v2** scales capacity (0.5–2 ACUs here) automatically and can
  scale to zero-ish cost when idle — keeping the "serverless" spirit of the
  rest of the stack, unlike a fixed-size RDS instance.
- The **Data API** lets Lambda run SQL over an HTTPS call
  (`RDSDataClient` / `ExecuteStatementCommand`) instead of opening a real
  TCP connection to the database. That means:
  - Lambda does **not** need to be placed inside the VPC (no cold-start ENI
    attachment delay, no NAT Gateway needed).
  - No connection pooling to manage from Lambda.
  - Credentials are handled via a Secrets Manager secret (auto-generated by
    CDK) — Lambda is only granted permission to use the secret + call the
    Data API, never the raw DB password.
- The `orders` table schema is created automatically at deploy time via a
  CDK `AwsCustomResource` that issues one `CREATE TABLE IF NOT EXISTS` call
  through the Data API — no bastion host, no manual `psql` session.

## 1. Install dependencies

```bash
npm install
```

## 2. Validate without touching AWS

```bash
npm test          # Jest tests against the synthesized CloudFormation template
npx cdk synth      # renders both stacks to cdk.out/ — pure local operation
```

## 3. Deploy to real AWS

You'll need AWS credentials configured (`aws configure` or env vars).

```bash
npx cdk bootstrap                 # one-time per account/region
npx cdk deploy AwsCdkProjectStack # deploy just the serverless pipeline
# or: npx cdk deploy --all        # deploy this stack + CdkS3Stack
```

**Heads up:** Aurora cluster + instance provisioning typically takes
5–15 minutes, noticeably longer than the DynamoDB version's deploy time.
That's expected — it's the one genuinely non-instant piece of this stack.

After it finishes, note the `ApiUrl` output — that's your base API URL,
something like:
```
https://abc123xyz.execute-api.us-east-1.amazonaws.com/prod/
```

## 4. Hit the API

**Create an order** (kicks off the whole async pipeline):
```bash
curl -X POST "<ApiUrl>orders" \
  -H "Content-Type: application/json" \
  -d '{"item": "wireless mouse", "quantity": 2}'
```
Response (immediate, status `202`):
```json
{
  "id": "b2f1...",
  "item": "wireless mouse",
  "quantity": 2,
  "status": "PENDING",
  "createdAt": "2026-07-22T10:00:00.000Z"
}
```

**Check its status** (poll this — status changes as the pipeline runs):
```bash
curl "<ApiUrl>orders/<id-from-above>"
```
- Right after creation: `"status": "PENDING"`
- A few seconds later: `"status": "PROCESSED"`, `"processed_at"` set
- Shortly after that: `"audited_at"` appears too, added by the
  EventBridge-triggered handler — proof the full chain
  (API → SNS → SQS → Lambda → EventBridge → Lambda, all reading/writing
  Postgres) ran end to end.

## 5. Inspect the database directly (optional)

No `psql`/VPC access needed — you can query through the Data API with the
AWS CLI, using the `DbClusterArn` and `DbSecretArn` stack outputs:

```bash
aws rds-data execute-statement \
  --resource-arn <DbClusterArn> \
  --secret-arn <DbSecretArn> \
  --database orders \
  --sql "SELECT * FROM orders ORDER BY created_at DESC LIMIT 10" \
  --format-records-as JSON
```

## 6. Watch it happen

```bash
aws logs tail /aws/lambda/<ProcessOrderFunction-name> --follow
aws logs tail /aws/lambda/<AuditOrderFunction-name> --follow
aws logs tail /aws/lambda/<OrderProcessedHandlerFunction-name> --follow
```
Function names are in `aws cloudformation describe-stacks` or the Lambda
console.

## 7. Tear down

```bash
npx cdk destroy AwsCdkProjectStack
```

## Note on local emulation (LocalStack)

LocalStack's free tier covers Lambda, SNS, SQS, EventBridge, and API Gateway
fine, but **Aurora Serverless v2 and the RDS Data API are LocalStack Pro
features**, not part of the free tier. If you want a fully-local run of this
particular version of the stack, the practical options are:
- Run a plain Postgres container locally (`docker run postgres`) and swap
  the Lambda DB calls to a regular `pg` client + connection string instead
  of the Data API — a bigger code change than "swap the backend," so it's
  not done here to keep the diff minimal.
- Use LocalStack Pro, which does emulate RDS Data API.
- Deploy to a real (cheap) AWS dev account — Aurora Serverless v2 at
  0.5 ACU minimum is inexpensive for a personal dev/test stack.
